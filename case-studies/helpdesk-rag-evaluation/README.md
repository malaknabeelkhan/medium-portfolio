# HelpDesk RAG Evaluation Framework

An educational project that implements a Retrieval-Augmented Generation (RAG) pipeline for IT helpdesk troubleshooting and evaluates both document retrieval and generated answers.

The project focuses on understanding the components of a RAG system and implementing evaluation metrics directly in Python rather than relying entirely on an existing RAG evaluation framework.

## Project Overview

The system uses a small IT helpdesk knowledge base containing four troubleshooting documents:

| Document ID | Topic |
|---|---|
| D1 | Wi-Fi connectivity troubleshooting |
| D2 | Printer troubleshooting |
| D3 | Windows password reset |
| D4 | DNS resolution troubleshooting |

Given a user question, the system retrieves relevant information from the knowledge base, constructs a context, generates an answer using a large language model (LLM), extracts claims from the answer, and evaluates the retrieval and generation stages.

## Technologies

- **Python** — implementation of the RAG pipeline and evaluation logic.
- **Ollama** — embedding generation and LLM inference.
- **nomic-embed-text** — embedding model used for document and query vectors.
- **ChromaDB** — persistent vector database used to store embeddings and retrieve relevant chunks.
- **Qwen 2.5 7B** — LLM used for answer generation and LLM-based evaluation.
- **Google Colab and Cloudflare Tunnel** — used to expose the Colab Ollama API to the local project during the experiments.

The project uses separate Ollama environments for local embedding generation and remote LLM inference through the Colab tunnel.

## Evaluation

The project evaluates retrieval and generation separately.

### Retrieval metrics

| Metric | Description |
|---|---|
| Precision@K | Number of relevant retrieved documents in the top K results divided by K. |
| Recall@K | Number of relevant retrieved documents in the top K results divided by the total number of relevant documents. |
| Mean Reciprocal Rank (MRR) | Average reciprocal rank of the first relevant result across the evaluation questions. |

### Generation metrics

| Metric | Description |
|---|---|
| Faithfulness | Estimates whether claims extracted from the generated answer are supported by the retrieved context. |
| Answer Relevance | Estimates how well the generated answer addresses the user's question. |
| Context Relevance | Estimates how useful the retrieved context is for answering the user's question. |

Generation metrics use an LLM as a judge. These scores are model- and prompt-dependent estimates, not objective ground truth.

## Final Recorded Results

The final recorded experiment used **K = 1** for retrieval.

### Retrieval results

| Query | Expected/retrieved document | Precision@1 | Recall@1 | Reciprocal rank |
|---|---|---:|---:|---:|
| Q1 — Printer offline | D2 | 1.000 | 1.000 | 1.000 |
| Q2 — Wi-Fi connection | D1 | 1.000 | 1.000 | 1.000 |
| Q3 — Windows password reset | D3 | 1.000 | 1.000 | 1.000 |
| Q4 — DNS/domain names | D4 | 1.000 | 1.000 | 1.000 |
| **Average** | | **1.000** | **1.000** | **1.000** |

### Generation results

| Query | Faithfulness | Answer Relevance | Context Relevance |
|---|---:|---:|---:|
| Q1 — Printer offline | 1.000 | 1.000 | 0.750 |
| Q2 — Wi-Fi connection | 1.000 | 1.000 | 0.750 |
| Q3 — Windows password reset | 1.000 | 0.850 | 0.500 |
| Q4 — DNS/domain names | 1.000 | 0.850 | 0.750 |
| **Average** | **1.000** | **0.925** | **0.688** |

### Interpretation

- For these four test questions, the expected document was ranked first in every case.
- The LLM judge assigned an average faithfulness score of 1.000 to the extracted claims.
- Answer relevance averaged 0.925.
- Context relevance averaged approximately 0.688. Q3 received a lower context-relevance score than the other questions.

These results apply only to this small test set. A perfect score on four questions does not establish that the retriever will perform equally well on a larger or more varied helpdesk dataset. Also, faithfulness is evaluated against the claims returned by the claim extractor; it does not independently verify every sentence in the answer.

## Setup

### Requirements

- Python 3.11
- Ollama installed locally for embedding generation
- An Ollama instance running in Google Colab for remote LLM inference
- A Cloudflare Tunnel to make the Colab Ollama API reachable from the local machine

Install the Python packages used by the project:

```bash
pip install chromadb ollama requests python-dotenv
```

Pull the embedding model into the **local** Ollama environment:

```bash
ollama pull nomic-embed-text
```

Make sure the Qwen model is available in the **Colab** Ollama environment:

```bash
ollama pull qwen2.5:7b
```

### Configure the environment

Create a `.env` file in the project root:

```env
COLAB_BASE_URL=https://YOUR-CURRENT-CLOUDFLARE-TUNNEL-URL
COLAB_MODEL=qwen2.5:7b
```

Do not commit `.env` or publish the tunnel URL. The Cloudflare Quick Tunnel URL is temporary and can change when the tunnel is restarted.

### Start the Colab connection

1. Start the Google Colab runtime containing the Ollama setup.
2. Start the Ollama service and the Cloudflare tunnel in that runtime.
3. Copy the newly generated `https://...trycloudflare.com` URL.
4. Update `COLAB_BASE_URL` in the local `.env` file with that current URL.
5. Keep the Colab runtime and tunnel running while the local evaluation is using the remote LLM.

If the tunnel disconnects, the existing URL may no longer work. Restart the tunnel, copy its newly generated URL, and update `COLAB_BASE_URL`. No code change is normally required just because the tunnel URL changed.

The tunnel exposes the Ollama API publicly while it is active. Use it only for this experiment, do not share the URL, and stop the tunnel when finished.

### Run the evaluation

From the project root, run:

```bash
python run_evaluation.py
```

`run_evaluation.py` is the project's entry point. It runs retrieval evaluation, generates answers for the evaluation questions, extracts claims, evaluates generation, and prints the results.

`main.py` is currently empty and is not used to run the project.

## Limitations

- The knowledge base contains only four helpdesk documents.
- The evaluation dataset contains only four questions.
- The final retrieval results use K = 1; results can differ with another K value.
- LLM-as-a-judge scores depend on the judge model and evaluation prompt.
- Claim extraction may omit parts of a generated answer, which can affect faithfulness evaluation.
- The Colab and Cloudflare connection is temporary and is intended for this educational experiment, not production deployment.
- The project has not been validated for production use.
